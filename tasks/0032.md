### Оцінка по категоріях

**Сильні сторони (що вже добре)**

Rust `Field` та `PhaseLatticeField` обидва використовують справжню SoA (Struct
of Arrays) — окремі `Vec<u8>` для theta, omega, amplitude, lock, entanglement,
plasmids. LUT-based математика (SINE_LUT, ENTROPY_LUT, `atan2_u8`) — правильне
рішення для WASM. Ping-pong буфери в WebGPU compute — канонічний pattern. Phase
Coherence Gate (9 invariants, golden traces) — це золотий стандарт регресійного
тестування для фізичного двигуна. `shedding_worker.ts` з zero-copy transfer —
грамотно. Документація онтологій (O8→O64) є живою специфікацією.

### Критичні проблеми (рефакторинг)

**1. Дублювання двох полів — `Field` vs `PhaseLatticeField`**

Це найбільший архітектурний борг. `Field` (legacy Cartesian x/y grid у
`simd_tick.rs`) і `PhaseLatticeField` (нова полярна координатна система у
`phase_lattice.rs`) співіснують. PHASE_COHERENCE_SPEC описує план міграції Stage
0–6, і судячи по коду, ти зараз між Stage 2–3. `Field` ще живий через
`execute_phase_bridge_tick`. Вектор — завершити Stage 3–6: перенести всю
bridge-логіку в `PhaseLatticeField`, retire `Field`.

**2. Дублювання внутрішніх функцій між `simd_tick.rs` і `phase_lattice.rs`**

Обидва файли містять ідентичні або майже ідентичні реалізації:

```rust
// Exists in BOTH simd_tick.rs AND phase_lattice.rs:
fn mix_u64(hash: &mut u64, value: u64) { ... }
fn phase_sin_i32(from_theta: u8, to_theta: u8) -> i32 { ... }
fn phase_cos_i32(from_theta: u8, to_theta: u8) -> i32 { ... }
fn q10_round(x: i32) -> i32 { ... }
fn q10_round_i64(x: i64) -> i64 { ... }
fn wrap_index(value: i32, modulo: usize) -> usize { ... }
fn clamp_byte(value: i16) -> u8 { ... }
fn wrap_phase(value: i16) -> u8 { ... }
```

Рефакторинг: виділити в `omega_core/src/utils.rs` як `pub(crate)`.

**3. Constants desync — `constants.rs` (Rust) vs `constants.ts` (TS)**

Константи визначені в двох місцях вручну:

```rust
// constants.rs
pub const KURAMOTO_COUPLING_BASE: i32 = 1024;  // = 1.0 * Q10
pub const MUTATION_BASE_COST: i32 = 50;
```

```typescript
// constants.ts
export const KURAMOTO_COUPLING_BASE = 1.0;
export const MUTATION_BASE_COST = 50;
```

Це класична проблема out-of-sync. Рішення: єдиний `substrate_constants.json` або
`constants.toml` як source-of-truth, з code-gen скриптом, що генерує обидва
файли під час build. Це повністю усуває ризик дивергенції фізики між Rust і
TS/WGSL шарами.

**4. `perturbation.rs` — hardcoded 256×256**

```rust
if tx >= 0 && tx < 256 && ty >= 0 && ty < 256 {
```

`Field::new(width, height)` дозволяє довільні розміри, але perturbation
захардкодила 256. Це latent bug — якщо хтось створить `Field::new(64, 64)`,
perturbation буде писати за межі. Виправлення: замінити на `field.width as i32`
та `field.height as i32`.

**5. `PlasmidRegistry` — глобальний мутабельний стан**

```typescript
// pure_lambda.ts — module-level global
export const PlasmidRegistry = new Map<bigint, SomaticNode>();
```

Це унеможливлює тестування ізольованих інстанцій, ускладнює серіалізацію і
повністю прив'язує Oracle до одного singleton. Рефакторинг: перемістити
всередину класу `SovereignOracle`, передавати як `this.plasmidRegistry`. Це
також відкриє можливість мати кілька Oracle-інстанцій для multi-agent resonance.

**6. `EvolutionPipeline` — відключений skeleton**

```typescript
// evolution.ts — завантаження шейдерів через fetch в рантаймі
const simulateShader = this.device.createShaderModule({
  code: await fetch("/shaders/compute_simulate.wgsl").then((r) => r.text()),
});
```

По-перше, шейдери повинні завантажуватися через Vite `?raw` import (як в
`phase_compute.ts`), не через `fetch`. По-друге, bind groups у `tick()` не
прив'язані до жодних реальних ресурсів (`// bind(0): fieldBuffer` — тільки
коментарі). Цей клас або не використовується, або є заглушкою. Необхідно або
повністю реалізувати, або видалити та відкласти як `TODO:`.

**7. `phase_network.ts` — тривіально підробляємий origin**

```typescript
const origin = "peer_" + Math.random().toString(36).substring(7);
const signature = fnv1a_64(`${hash}:${targetBucket}:${origin}:${SALT}`);
```

Origin генерується самим відправником і включається у підпис. Атакуючий просто
генерує свій origin і підписує ним — підпис буде валідним. Це не cryptographic
proof-of-work. Для серйозного захисту потрібні keypair (Ed25519) і
challenge-response. Поточна система захищає лише від випадкових колізій, не від
навмисних атак.

**8. `dom.ts` — пряме читання фізичних констант у HUD**

```typescript
// dom.ts — coupling між HUD і physics constants
DOM.hEndocrineVal.replaceChildren(
  `K: ${KURAMOTO_COUPLING_BASE.toFixed(2)} | M: ${
    MUTATION_BASE_COST.toFixed(1)
  }`,
);
```

HUD-модуль напряму імпортує фізичні константи. Правильно — передавати
`PhysicsState` об'єкт у `updateHomeostasisHUD(entropy, energy, physicsState)`,
зберігаючи принцип dependency inversion.

**9. `index.html` — застарілий title**

```html

```

Система вже на Ontology 42/Era 64. Дрібниця, але свідчить про drift між
документами і кодом.

### Рекомендації по SoA + SIMD оптимізації

`PhaseLatticeField` вже SoA — це правильно. Але є кілька векторів для глибшої
оптимізації:

**Ordering для cache locality**: Поточний layout (harmonic-major → rho-major →
sector) оптимальний для fossilization (copy_within суміжних блоків), але для
Kuramoto tick гарячий шлях — це neighbors по sector у межах одного rho-шару.
Варто розглянути рho-major → sector → harmonic якщо переважає neighborhood
access.

**WASM SIMD для Rust fallback path**: Додати в `Cargo.toml`:

```toml
[target.'cfg(target_arch = "wasm32")'.dependencies]
# Enable SIMD128 for WASM target
```

І в `lib.rs`:

```rust
#[cfg(target_arch = "wasm32")]
use std::arch::wasm32::*;
```

Тоді у `execute_phase_lattice_tick` можна обробляти 16 theta-байт за один v128
операнд, що дає ~8–16x прискорення Rust fallback path (до WebGPU ініціалізації
або для малих grid).

**Plasmid u64 → два окремих u32 масиви**: Plasmids як `Vec<u64>` не вирівнюється
з u8-масивами для SIMD. Розділити на `plasmid_low: Vec<u32>` та
`plasmid_high: Vec<u32>` дасть краще SIMD alignment і спростить WebGPU binding.
