# Task 0154: Era 1680 — Translation Policy Investigation Loop

## Status: COMPLETED | Priority: HIGH

## Context
Era 1650 created policy drift events, Era 1660 moved claims over the
mesh, and Era 1670 converted drift events into warrant proposals. The
pieces were still separate. Operators needed one loop that ingests
policy claims and emits proposal payloads with full telemetry.

## Objective
1. Decode mesh policy-claim bodies.
2. Observe claims in `TranslationPolicyMonitor`.
3. Collect fresh drift alarms.
4. Build proposals through `TranslationPolicyWarrantBridge`.
5. Emit proposals through a caller callback.

## Acceptance Criteria

- [x] Malformed bodies are counted and ignored.

### 5. Tests ✅
- [x] End-to-end loop test covers claim → monitor → warrant → emit.
- [x] Targeted 1650→1680 test group remains green.

## Design Notes
- **Why no hidden mesh dependency?** The loop accepts claim objects or
  body JSON. Applications can wire it to WebRTC events, tests, or future
  substrate relays without changing core logic.
- **Why track seen drift events in the loop and also dedup in the
  bridge?** The loop avoids repeated work for the same monitor alarm.
  The bridge still protects downstream emitters if loop state is reset.
- **Why no quarantine here?** The loop emits proposals only. The Senate
  and existing quarantine lifecycle remain the enforcement boundary.
