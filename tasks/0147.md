# Task 0147: Era 1610 — Schema-Aware Multi-Sink Wiring

## Status: COMPLETED | Priority: HIGH

## Context
Eras 1580/1590/1600 each provided a layer for multi-domain
forensic operation but didn't compose by default. Era 1610
wraps them into a single `SchemaAwareMultiSinkInvestigator`
that auto-enforces schema compatibility on every cross-sink
operation.

## Objective
1. `SchemaAwareMultiSinkInvestigator` class composing
   Era 1580 + 1590 + 1600.
2. `addSink(id, schema_string, opts)` with atomic
   register-or-rollback semantics.
3. `observePeerAnchor` validates compatibility before
   forwarding; optional `peer_schema_string` for legacy compat.
4. Per-rejection telemetry counters.
5. Discovery helpers: `sinksByName`, `compatibleSinks`,
   `schemaOf`.
6. Aggregated `summary` for HUD.

## Design Notes
- **Why composition over inheritance?** `MultiSinkInvestigator`
  has its own state and lifecycle; subclassing would tangle
  Era 1610's schema concern into Era 1580's orchestration.
  Composition lets each layer evolve independently and lets
  operators using only Era 1580 stay unchanged.
- **Why does `addSink` register the schema BEFORE the
  multi-sink layer?** Atomicity. If we registered in multi
  first and then schema parsing failed, we'd have a sink
  with no recorded schema — corrupt state. Registry validation
  is faster + side-effect-free until the call returns; if it
  passes, the multi registration is overwhelmingly likely to
  succeed. Rolling back the registry on the rare multi
  failure keeps the invariant clean.
- **Why is `peer_schema_string` optional?** Migration paths.
  Existing peers (or third-party integrations) won't announce
  schemas immediately. Forcing schema announcement
  out-of-the-gate would block deployment. Optional with
  bypass-on-omit lets operators phase in enforcement.
- **Why rejection counters bucketed by category instead of a
  single "total_rejected"?** Different categories warrant
  different operator response: `unknown_sink` is a routing
  bug; `major_mismatch` is a peer-version-mismatch; `name_
  mismatch` is potential cross-domain attack. Separate
  counters surface the right signal to the right alert.
- **Why expose `multi` and `registry` as public readonly
  fields?** Drilldown access for tests and HUDs that need
  details the wrapper's summary doesn't surface. Read-only is
  enough — operators shouldn't mutate either independently of
  the wrapper, but inspection is fine.

## Next Era Trigger
**Era 1620: Cross-Domain Translation Bridge.** Era 1610
permits minor-version drift but refuses major mismatches.
The next gap is when operators NEED to bridge between two
incompatible majors during a migration:
- Define a `SchemaTranslator` interface that maps records
  from one schema to another.
- Operator-supplied translators for specific schema pairs
  (e.g. `"alarms:v1.x" → "alarms:v2.x"`).
- Multi-sink investigator consults the translator registry
  when an incoming peer announces a non-compatible major,
  applies translation, then forwards via the standard path.
- Tests covering translation success, idempotent translations,
  and refusal when no translator is registered.
