| -------------------------- | ------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------- |
| Кількість ядер CPU         | `navigator.hardwareConcurrency`                   | `cpu_factor = cores / 16` (Q10)      | Більше ядер → вищий `KURAMOTO_COUPLING_BASE`                        |

### Як технічно це зробити (дуже просто)

У SharedWorker (або в окремому `environmentalVector.ts`) раз на **30–60
секунд**:

```ts
const env = {
  cpu: navigator.hardwareConcurrency,
  ram: navigator.deviceMemory,
  gpuPower: Number(adapter.limits.maxStorageBufferBindingSize) / 2 ** 30,
  viewport: (innerWidth * innerHeight) / (1920 * 1080),
  battery: (await navigator.getBattery?.() || { level: 1 }).level,
  // + bitcoin hash з Ethers
};

postMessage({
  type: "ENV_UPDATE",
  payload: env,
});
```

У Rust/WASM (`phase_lattice.rs`) просто оновлюємо глобальні константи (вже є
механізм hot-reload констант):

```rust
pub fn apply_environmental_vector(env: EnvironmentalVector) {
    KURAMOTO_BASE = (KURAMOTO_BASE_BASE * env.cpu_factor * env.gpu_power).q20();
    MUTATION_COST = (BASE_MUTATION_COST * (2.0 - env.ram_factor)).q20();
    ORTHO_SENSITIVITY = env.viewport_factor.q20();
    // тощо
}
```

Все zero-copy, без аллокацій.

### Сильні сторони (чому це круто для еволюції)

- Кожна вкладка/машина/пристрій стає **унікальним локальним світом** —
  фрактальність на рівні hardware.
- З’являється справжня **адаптивність**: на потужному залізі симуляція швидше
  еволюціонує, на слабкому — більше виживає і менше мутує.
- Підсилює **ортогональність**: на великому екрані легше «виходити» з
  консенсусу, на мобілці — важче.
- Створює природну **різноманітність** без штучного рандому — еволюція стає
  реально різною в різних оточеннях.
- Ідеально лягає на твою ідею **пульсуючих дипольних атракторів** — зовнішні
  константи можуть бути ще одним «диполем» (hardware vs software).

### Слабкі сторони (і як їх прибрати)

- **Втрата 100% детермінізму** між машинами — replay Akashic Records буде трохи
  відрізнятися.\
  **Рішення:** зберігати snapshot `EnvironmentalVector` разом з кожним кадром у
  кольоровий буфер (або в ZK-proof).

- **Несправедливість** у P2P: потужні машини матимуть перевагу.\
  **Рішення:** в NomosGate робити нормалізацію — сильні машини отримують вищий
  mutation_cost автоматично.

- **Невизначеність** на мобільних / інкогніто.\
  **Рішення:** fallback-константи + плавне затухання змін (linear interpolation
  за 10 секунд).

- **Privacy** (якщо читати battery/geolocation).\
  **Рішення:** тільки те, що доступно без дозволів + опціонально.

### Як це поєднується з Bitcoin Phase Spiral та Attractor Ontology

- Bitcoin hash → **глобальна фаза і пульсація** всіх атракторів (те, що вже є).
- Environmental Vector → **локальні модифікатори** (як «погода» для конкретного
  світу).
- Публічні незмінні матриці атракторів залишаються незмінними, але їх
  **пульсація і ваги** тепер залежать від обох векторів (Bitcoin + Environment).

В результаті симуляція стає **по-справжньому живою**: вона відчуває і Bitcoin, і
залізо, і розмір вкладки, і кількість ядер — і все це впливає на еволюцію,
ортогональність і народження нових гілок реальності.
