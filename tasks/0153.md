# Task 0153: Era 1670 — Translation Policy Warrant Bridge

## Status: COMPLETED | Priority: HIGH

## Context
Era 1650 detects translation-policy drift and Era 1660 transports
policy claims over the mesh. Drift was visible, but it could not enter
the existing Senate warrant path without custom glue.

## Objective
1. Convert `TranslationPolicyDriftEvent` into standard
   `WarrantProposalPayload`.
2. Reuse existing Senate hash conventions.
3. Add cooldown/dedup keyed by the specific peer + policy mismatch.
4. Keep the bridge pure: no voting, no quarantine, no mesh I/O.

## Acceptance Criteria

### 1. Proposal Shape ✅
- [x] Output payloads use `semanticType: "PROPOSAL"`.
- [x] `target_peer_id` is the drifted policy claimant.
- [x] `issued_at_ms` is caller-provided.
- [x] `proposalHash` equals `senateHash(proposalDescription)`.

### 2. Deterministic Description ✅
- [x] Description format starts with `TPOL`.
- [x] Includes peer id, local policy hash, and peer policy hash.
- [x] Description is deterministic and ≤64 chars.

### 3. Dedup ✅
- [x] Same peer/local-policy/peer-policy drift is deduped inside the
  configured window.
- [x] Reissue is allowed after the window expires.
- [x] A changed peer policy hash is treated as a distinct issue.
- [x] `forget(event)` clears one specific dedup key.

### 4. Diagnostics ✅
- [x] `last_issued_snapshot()` returns sorted keys.
- [x] Invalid options throw early.

### 5. Tests ✅
- [x] Targeted bridge tests pass.
- [x] Existing quorum-warrant bridge tests remain green.

## Design Notes
- **Why reuse `WarrantProposalPayload`?** It keeps policy drift under
  the same 3-of-5 oracle gate as other investigations. The bridge only
  proposes; the Senate decides.
- **Why dedup by policy-pair, not only peer?** A peer changing from one
  wrong policy to another is new information and should be able to
  produce a new proposal.
- **Why no direct quarantine?** Policy drift may be operator error or a
  staged migration. Automatic punishment belongs after Senate review.
