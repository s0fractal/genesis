# Task 0146: Era 1600 — Schema-Validated Cross-Sink Sync

## Status: COMPLETED | Priority: HIGH

## Context
Era 1390's `applyEventDelta` merges any sender's entries
without checking content-domain identity. Era 1600 wraps it
with schema validation so multi-domain deployments can't
silently cross-pollinate.

## Objective
1. `SchemaTaggedDelta` and `SchemaTaggedHashList` wrappers.
2. `applyEventDeltaWithSchema` validates compatibility +
   delegates.
3. Typed rejection codes for downstream routing.
4. `SchemaAwareSinkSync` class binding sink + schema.

## Design Notes
- **Why typed rejection codes instead of error strings?**
  Different rejection modes warrant different remediation:
  retry (protocol error) vs reroute (content error) vs alert
  the operator (collision/corruption). String-based reasons
  force callers to do brittle string matching; typed codes
  encode the policy directly into the type.
- **Why `null` from `computeDeltaForPeer` on incompatibility
  rather than throwing or returning an error?** A peer
  announcing the wrong schema is a routine-routing fact, not
  an exceptional event. Treating it as an error path would
  spam logs and force callers to write try/catch around what's
  effectively "this peer isn't relevant to me". Null is the
  cleanest "stay silent" signal.
- **Why preserve Era 1390 unchanged instead of adding schema
  fields directly to EventDelta?** Backward compatibility.
  Existing tests, code paths, and external consumers of
  `EventDelta` continue to work. The schema layer composes on
  top — callers opt in by using the wrapper. Editing
  EventDelta in place would have rippled into 19+ existing
  tests (Era 1390's whole suite).
- **Why is collision rejection surfaced as `apply-failed`
  rather than its own variant?** Era 1390's `applyEventDelta`
  already returns a discriminated union with `reason` strings.
  Mirroring that into top-level Era 1600 codes would duplicate
  every Era 1390 failure mode. Wrapping them in `apply-failed`
  keeps Era 1600's surface focused on the schema layer; the
  `underlying` string carries Era 1390's specifics for
  diagnostics.
- **Why does `SchemaAwareSinkSync` re-export
  `underlyingSyncSchema`?** Diagnostic. Operators reading
  telemetry want to know which Era 1390 protocol version is
  being spoken under the wrapper. A future Era 1700 might
  bump Era 1390's version; the aware class will then naturally
  surface the new value without per-call instrumentation.
