# 🌌 OMEGA-64: Теорія Обмежень & Бюджету Ресурсів (Theory of Constraints)

## 1. Абсолютні Ліміти Апаратного Забезпечення (Hardware Ceilings)
OMEGA-64 діє за принципами кібер-біології: розмір "всесвіту" (сітки) не визначається забаганками розробника, він диктується **фізичною реальністю хоста** (RAM/VRAM).

### Бюджет Пам'яті (Memory Constraints)
- **Bottom-Up Limit:** `adapter.limits.maxStorageBufferBindingSize` (WebGPU ліміт одного буфера).
- **VRAM Boundary:** Якщо WebGPU дозволяє виділити максимум `256 MB` під один буфер, а розмір одного агента `24 байта`, то максимальна кількість агентів у всесвіті становить `N_max = 256MB / 24B ≈ 10,666,666` агентів.
- **Дарвінівський Ліміт:** Ми беремо `80%` від `N_max` як жорстку межу розширення матриці (`max_elements`), залишаючи 20% під "еволюційний дихальний об'єм".

## 2. Відмова від Картезіанських Звичок (Power of Two Alignment)
Типове людське мислення тяжіє до "гарних" чисел: 360 градусів (секторів), 100 відсотків, 10 вимірів. Але для силікону ці числа — ворожі.

### Чому $2^n$ — це закон OMEGA-64?
У нашому ядрі (`phase_lattice.rs` / `compute_kuramoto.wgsl`) фазовий кут $2\pi$ закодований як **256** (один байт або `u32 & 255`).
Це дає нам безкоштовні переповнення! $(250 + 10) \& 255 = 4$. Нам не потрібні повільні `% 256` чи `if angle > 360 { angle -= 360 }`.

Якщо ми зробимо `sectors = 360`, ми зруйнуємо цю оптимізацію:
```rust
// ❌ ПОГАНО (sectors = 360)
// angle (0..255). Пошук сектора вимагає ділення на константу, яка не є степенем 2.
let sector_idx = (angle as i32 * 360) / 256; // Повільно на ALU!
```

```rust
// ✅ ЕВОЛЮЦІЙНО ПРАВИЛЬНО (sectors = 256 або 128 або 64)
// Якщо sectors = 256:
let sector_idx = angle; // O(1) Безкоштовно!

// Якщо sectors = 128 (Вдвічі менший радіус через обмеження пам'яті телефону):
let sector_idx = angle >> 1; // O(1) Один бітовий зсув!

// Якщо sectors = 64
let sector_idx = angle >> 2; // O(1) Один бітовий зсув!
```

**Правило:** Усі геометрічні константи матриці (`sectors`, `radial_bins`, `harmonics`, `tau_depth`) ПОВИННІ бути **степенями двійки ($2^n$)**, щоб обчислення координат у пам'яті працювали через бітові зсуви (`>>`) та бітові маски (`& (size - 1)`).

## 3. Матриця Похідних Розмірностей (Derived Dimensions)

Сітка більше не хардкодиться константами. При завантаженні або зміні розміру вікна браузера, PhaseLattice виконує такий алгоритм:

1. Отримати `maxVRAM`.
2. Обчислити `max_cells = maxVRAM / 24_bytes`.
3. Визначити степені двійки для матриці "Зверху-Вниз":
   - `tau_depth` = 8 (Жорсткий ліміт для історичного сліду ZK-Proofs).
   - `harmonics` = вибрати найближчу $2^n \le 16$, щоб зберігати "поліфонію".
   - `radial_bins` = вибрати найближчу $2^n$ (напр. 64 або 128).
   - `sectors` = Збільшувати $2^n$, поки `sectors * radial * harmonics * tau <= max_cells`.
   (На старих телефонах це буде сітка 64x64, на потужних GPU — 256x256 і більше).

## 4. Локальні Bitmask Кеші (The Reactive SignalStore)
Щоб Rust та WGSL не обчислювали "розмірності" на кожному кадрі:
- Rust тримає `LatticeMetrics` (де всі множення вже виконані).
- Коли UI / Мережа міняє "щільність", генерується подія, що встановлює `dirty_flags |= 0b0001;`.
- Під час наступного $\tau$ тіку Rust рекалькулює `LatticeMetrics` (відкидаючи зайвих агентів через Дарвінізм, щоб влізти в новий ліміт) і серіалізує ці константи напряму в `Uniform Buffer` для WGSL.
- **Жодних виділень пам'яті (allocations)** на льоту! Тільки чиста математика над заздалегідь підготовленим SharedArrayBuffer.
