# Task 0143: Era 1570 — Quarantine Lifecycle Bridge

## Status: COMPLETED | Priority: HIGH

## Context
Era 1560 provides `loop.excludePeer` / `includePeer`. Era 1570
wires those to the existing quarantine event flow so the
autonomous loop runs end-to-end without manual operator calls.

## Objective
1. `EventSource` interface + `LocalEventSource` test impl.
2. `QuarantineLifecycleBridge` class with start/stop lifecycle.
3. Auto-call `loop.excludePeer` on `quarantine-engaged` events.
4. Auto-call `loop.includePeer` on `quarantine-resolved` events.
5. Malformed-payload tolerance + telemetry counters.
6. Configurable event names.

## Acceptance Criteria

### 1. Event Source ✅
- [x] Minimal `EventSource` interface (addEventListener +
  removeEventListener).
- [x] `LocalEventSource` test impl with `dispatch(type, detail)`
  helper.

### 2. Bridge Class ✅
- [x] Starts inactive; `start()` subscribes to both events;
  idempotent.
- [x] `stop()` unsubscribes; idempotent.
- [x] `isActive()` query.
- [x] `telemetry()` snapshot.

### 3. Routing ✅
- [x] `quarantine-engaged` event with `{peer_id: number}` →

- [x] `quarantine-resolved` event → `loop.includePeer(peer_id)`.
- [x] Events after `stop()` are no-ops (listeners removed).

### 4. Robustness ✅
- [x] Missing `peer_id`, non-number, null detail → counted as

- [x] Configurable `engaged_event_name` /
  `resolved_event_name` opts; default names match convention.

### 5. Tests ✅
- [x] 12 Deno tests covering: starts inactive, start/stop,

  payload counted, telemetry counts, stop unsubscribes,

  exclusion→no-re-fire scenario, schema constant.

## Design Notes
- **Why a transport-agnostic `EventSource` instead of using
  `globalThis` directly?** Hermetic tests. globalThis listeners
  pollute the test runtime and require careful cleanup;
  LocalEventSource lets each test get its own clean source
  with no cross-test bleeding. Production wires globalThis
  trivially.
- **Why does the bridge own no internal state about which
  peers are excluded?** The loop already tracks that. Mirror
  state would create a sync hazard. The bridge is just a
  forwarding layer: events in → loop calls out.
- **Why is malformed-payload tolerance important?** External
  dispatchers (especially ones that evolve over time) can send
  unexpected shapes. Crashing the entire investigation loop
  on a bad event would create an availability hole proportional
  to the rate of bad events. Logging + skipping is the
  defensive default.
- **Why configurable event names?** Different parts of the
  codebase have used different names historically
  (`era1080-quarantine-engaged` was one convention). Letting
  operators tune the names lets them migrate without a code
  change.
- **Why no internal idempotency check (e.g. dedupe events for
  the same peer)?** Era 1560 already made `excludePeer` /
  `includePeer` idempotent. Re-engaging an already-excluded
  peer is a no-op at the loop level. Adding dedupe at the
  bridge would create another piece of state to keep in sync.
