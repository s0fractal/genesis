# Task 0150: Era 1640 — Translation-Aware Multi-Sink Discovery

## Status: COMPLETED | Priority: HIGH

## Context
Era 1630 made a single schema-aware sync path translation-capable.
But operator orchestration still only knew about same-major compatible
sinks. A deployment could apply translated deltas manually, yet the
multi-sink layer could not discover migration targets or report
translation telemetry.

## Objective
1. Give `SchemaAwareMultiSinkInvestigator` a shared
   `SchemaTranslatorRegistry`.
2. Expose translation-aware discovery beside existing compatible
   discovery.
3. Keep the default schema firewall closed for unregistered pairs.
4. Surface per-sink translation/drop/applicability telemetry.

## Acceptance Criteria

### 1. Shared Registry ✅
- [x] Constructor accepts an optional `SchemaTranslatorRegistry`.
- [x] `registerTranslator(...)` delegates to the shared registry.
- [x] Existing callers that pass only `emit` still work.

### 2. Discovery ✅
- [x] `translatableSinks(source_schema)` returns only explicitly
  registered migration targets.
- [x] `compatibleOrTranslatableSinks(source_schema)` returns direct
  compatible sinks plus registered migration targets.
- [x] Discovery remains deterministic and sorted.

### 3. Observation Gate ✅
- [x] Same-major compatible observations still pass unchanged.
- [x] Major mismatch still refuses without sender→local translator.
- [x] Major mismatch passes when sender→local translator is registered.
- [x] Name mismatches and malformed schemas remain rejected.

### 4. Telemetry ✅
- [x] Summary exposes registered translator pairs.
- [x] Summary exposes total translated/dropped counts.
- [x] Summary exposes per-sink translated/dropped/applicable-observation

- [x] `recordTranslationApply(...)` lets Era 1630 apply outcomes feed

### 5. Tests ✅
- [x] Discovery tests for translatable and compatible-or-translatable

- [x] Observation tests for registered vs unregistered major mismatch.
- [x] Translation telemetry tests for apply counts and registered pair

- [x] Existing Era 1610 behavior remains green.

## Design Notes
- **Why discovery only scans same-name sinks?** Era 1640 is a migration
  operator layer. Cross-domain translators can still exist at Era 1620,
  but multi-sink auto-routing should not silently bridge unrelated
  content domains.
- **Why observe anchors without transforming them?** Anchor observation
  is quorum metadata, not event content. The actual event translation
  remains owned by Era 1630's apply path; Era 1640 records that the
  observation was accepted due to a registered migration policy.
- **Why keep `SCHEMA_AWARE_MULTI_SCHEMA = OMEGA-1610/v1`?** The public
  schema-aware multi-sink contract remains additive. Era 1640 extends
  local orchestration and telemetry, not the base schema format.

## Next Era Trigger
**Era 1650: Translation Policy Digest & Drift Alarm.** Era 1640 makes
translation policy operational, but that policy is still local state.
The next leverage point is policy observability:
