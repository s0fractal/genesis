# Task 0095: Era 1090 — Senate Warrant Issuance Protocol

## Status: COMPLETED | Priority: HIGH

## Context
Era 1080 (Codeicide Law) defines the *gate* — given a presented warrant
hash + AYE bitmask, is an action against agent X lawful? But it does
not define how a warrant gets ISSUED in the first place. Until now, a
peer could compute a warrant hash from any (genome, action, quorum)
triple, but there was no on-chain proof that the Senate actually voted
on it.

Era 1090 closes this loop.

## Objective
Provide the Senate with a formal procedure for issuing warrants:
peers raise a `WARRANT_PROPOSAL`, canonical oracles cast `WARRANT_VOTE`s,
and when ≥ required_threshold AYE bits accumulate, the kernel
deterministically computes and stores the canonical Codeicide warrant.
JS/mesh can then refuse to relay TERMINATE/MUTATE plasmids whose
warrant hash does not appear in the issued ledger.

## Design Notes
- **`required_threshold` is per-proposal, not per-protocol.** This
  acknowledges that the issuer knows in advance whether the target is
  sanctuary (threshold 3) or ancient (threshold 4); the Codeicide gate
  enforces the actual minimum at presentation time. A proposal raised
  with threshold 3 against an ancient target will be issued by 3 AYEs
  but rejected by Codeicide when presented, which is the correct
  failure mode.
- **NAY does not reject; it just clears that oracle's AYE bit.** The
  proposal stays open until all five oracles have voted (capped by the
  required_threshold reaching) or until `expire_old` reaps it. This is
  intentional: an oracle that changes its mind should be able to flip
  AYE → NAY and back without permanently invalidating the proposal.
- **`reason` text stays off-chain.** The kernel only stores
  `reason_hash` (FNV-1a-32 of the bytes). Peers retain the full text
  in JS for display + auditability; the protocol verifies provenance
  without trusting content (consistent with the Era 1070 debate ledger
  model).
