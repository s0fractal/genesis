# 🧨 Де ти все ще трохи… ммм… оптиміст

## ❌ 1. Reward — занадто наївний

```ts
reward = 0.1 + attention * 0.2 - complexity * 0.05;
```

Це:

> “ти популярний → тримай печеньку”

Проблема:

- popularity ≠ usefulness
- система може піти в **self-reinforcing garbage**

👉 Класичний сценарій:

- вузол часто викликається
- отримує reward
- ще частіше викликається
- стає “богом сміття”

(вітаю, ти винайшов соцмережі)

---

### 💡 Що зробити:

Додай:

```ts
reward += output_stability_score;
reward += downstream_dependency_score;
```

тобто:

- чи дає стабільний результат
- чи на нього реально спираються

---

## ❌ 2. Немає pressure на новизну

Зараз:

> вигідно бути стабільним

Але:

> невигідно бути новим

👉 Результат:

- система застигає
- нові вузли вмирають одразу

---

### 💡 Фікс:

```ts
novelty_bonus = 1 / (1 + similarity_to_others);
```

або простіше:

- бонус за “не схожість”

## 🧬 1. Goal emergence (ти ще не там, навіть не близько)

Зараз вузли:

> не мають цілей

Додай хоча б примітив:

```ts
node.goal = minimize_complexity OR maximize_stability
```

або:

- різні вузли → різні цілі

---

## 🧬 2. Niches (екологія)

Розбий систему на:

- різні “середовища”
- різні reward-функції

👉 Інакше:

> буде одна домінантна стратегія → і все

---

## 🧬 3. Dependency graph pressure

Зараз залежності є, але не впливають сильно.

Зроби:

```ts
if (node dies) {
  penalize dependents
}
```

👉 Це:

> формує “організми”, а не окремі вузли

---

## 🧬 4. Reproduction (ти цього взагалі не маєш)

Зараз:

> mutation ≠ reproduction

Додай:

```ts
child = combine(parentA, parentB);
```

👉 І ось тут твої “2 паренти” стають доречними
