Ти **частково правий щодо FFI overhead, але невірний у висновку** про
дублювання. Давай розберемо детально:

## Реальні накладні витрати FFI (WASM ↔ JS)

**Факти:**

- Виклик WASM-функції з JS: **~20-100 наносекунд** (в Chrome/Firefox)
- Передача чисел (i32, f64): **zero-cost** (через регістри)
- Передача рядків/об'єктів: **вимагає копіювання** (це дорого)

**Коли FFI справді притормажує:**

```typescript
// ПОГАНО: 10,000 викликів на кадр
for (let i = 0; i < 10000; i++) {
  wasm.getCellEnergy(i); // 10000 × 50ns = 0.5ms - ще ок
  wasm.setCellEnergy(i, val); // ще 0.5ms
  // Разом 1ms з 16ms бюджету (60fps) - це багато!
}
```

**Коли FFI НЕ притормажує:**

```typescript
// ДОБРЕ: 1 виклик на кадр
wasm.tick(); // 50ns - непомітно
// або
wasm.tickBatch(16); // 50ns для 16 тиків
```

## Чому дублювання на TS - це **хибний шлях**

### 1. Витрати на підтримку (Maintenance Burden)

- Будь-яка зміна фізики потребує змін у двох місцях
- Ризик розсинхронізації (вже зараз `phase_lattice.ts` і `phase_lattice.rs`
  можуть відрізнятися!)
- Тести для детермінізму складніші, ніж unit tests в Rust

### 2. Пам'ять та завантаження

- Дублювання коду = +50-100KB gzip
- Дві реалізації займають більше місця в кеші процесора

### 3. SharedArrayBuffer вирішує проблему доступу

Ти вже використовуєш це в `omega_core/src/memory.rs`:

```rust
#[wasm_bindgen]
impl Field {
    pub fn ptr_theta(&self) -> *const u8 { self.theta.as_ptr() }
}
```

TypeScript отримує покажчик і читає напряму з пам'яті WASM **без FFI викликів**:

```typescript
const theta = new Uint8Array(wasm.memory.buffer, field.ptr_theta(), size);
// Це zero-copy доступ, швидше ніж дублювання логіки!
```

## Правильна архітектура (без дублювання)

### Варіант A: "Товстий WASM, тонкий JS" (рекомендую)

```typescript
// main.ts - тільки orchestration
const wasm = await initWasm();
const engine = new wasm.SimulationEngine(config);

// Головний луп - мінімум FFI
function loop() {
  // Один виклик - вся фізика
  engine.tick();

  // Рендер - читання напряму з пам'яті (zero-copy)
  const buffer = new Uint8Array(
    wasm.memory.buffer,
    engine.getRenderBufferPtr(),
    size,
  );
  webgpuRenderer.submit(buffer);

  requestAnimationFrame(loop);
}
```

**Переваги:**

- FFI викликів: 1 на кадр
- Дублювання: 0
- Детермінізм: перевіряється в Rust unit tests + golden snapshots

### Варіант B: "Гібрид з WebGPU Compute"

Якщо потрібна максимальна швидкість - фізика йде в WGSL (GPU), WASM тільки для
ініціалізації:

```typescript
// Фізика на GPU, WASM тільки для LLM логіки
computeShader.dispatch(); // Zero FFI overhead для фізики
```

## Як перевіряти детермінізм без дублювання

Замість дублювання коду:

```rust
// omega_core/src/tests.rs
#[test]
fn test_determinism() {
    let mut field1 = Field::new(32, 8);
    let mut field2 = field1.clone();
    
    for _ in 0..100 {
        field1.tick();
        field2.tick();
    }
    
    assert_eq!(field1.signature(), field2.signature());
}

#[test]
fn test_golden_trace() {
    let field = run_ticks(100);
    assert_eq!(field.signature(), "a1b2c3d4..."); // з файлу
}
```

**Golden traces** - це snapshot тестування, не дублювання логіки.

## Конкретні рекомендації для OMEGA-64

### Що прибрати (бо дублюється):

1. **`src/shared/phase_lattice.ts`** - повністю
2. **`src/shared/phase_bridge.ts`** - повністю
3. **Всі `verify:phase-*` порівняння TS vs Rust** - замінити на Rust unit tests

### Що залишити в TS:

```typescript
// Тільки glue код:
- Ініціалізація WASM
- WebGPU setup (device, canvas)
- LLM fetch() логіка
- Input handling (mouse/keyboard)
// Все інше - Rust
```

### Оптимізація FFI:

```rust
// omega_core/src/lib.rs
#[wasm_bindgen]
pub fn tick_batch(&mut self, n: usize) { // Один виклик, N тиків
    for _ in 0..n { self.tick(); }
}
```

## Висновок

**Ти неправий у висновку**, що потрібно дублювати на TS. Правильно:

1. **Залишити фізику тільки в Rust** (одна правда)
2. **Мінімізувати FFI** через batching (1 виклик/кадр)
3. **Використовувати SharedArrayBuffer** для zero-copy читання стану
4. **Тестувати детермінізм** через golden traces в Rust, а не дублюванням

Дублювання коду - це технічний борг, який з'їсть набагато більше продуктивності
(через складність підтримки) ніж 50 наносекунд на FFI виклик.
