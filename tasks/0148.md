# Task 0148: Era 1620 — Cross-Domain Translation Bridge

## Status: COMPLETED | Priority: HIGH

## Context
Era 1610 enforces strict schema compatibility, refusing major
mismatches. Era 1620 closes the migration-window gap with
explicit, opt-in translators per schema-pair.

## Objective
1. `SchemaTranslator` function type.
2. `SchemaTranslatorRegistry` keyed by `(name, major)` pairs.
3. `translateBatch` helper for sync paths.
4. Refusal of identical-pair, duplicate, malformed registrations.

## Design Notes
- **Why `(name, major)` as the translator key instead of
  full `(name, major, minor)`?** Minor versions are
  permissive (Era 1590 rule) — same content within a major
  with possibly extra fields. A single v1 → v2 translator
  handles every minor pair without operators having to
  register N×M translators for N v1.x and M v2.x minors.
- **Why refuse identical-compatible-pair registrations?**
  Programmer error. If source and target are already
  compatible, no translation is needed. Letting it register
  would create a translator that's never invoked (the
  identity fast-path always wins) — confusing dead code.
- **Why does `translateBatch` refuse different-name pairs
  without a translator (rather than passing through)?**
  Cross-domain leaks are the precise threat Era 1610 closed.
  Falling back to "no translator + different name = pass
  through" would re-open the hole. Operators MUST opt in
  explicitly to cross-domain bridging.
- **Why is chained translation deferred?** The most common
  use case (one major migration at a time) is direct-pair.
  Chained translation needs path-finding, cycle detection,
  and clear error signaling — substantial scope for a use
  case operators may never need. YAGNI.
- **Why does the translator receive both `source` and
  `target` schemas as args?** A translator might need to
  branch on minor versions (e.g. v1.7-and-up has a field
  that v1.0-1.5 doesn't). Passing the full schema lets the
  translator inspect minor/name without caller bookkeeping.
