# Task 0130: Era 1440 — Cross-Substrate Convergence Smoke

## Status: COMPLETED | Priority: HIGH

## Context
Eras 1400-1430 asserted cross-substrate parity at primitive
levels (FNV anchors, frame types, kind-tag packing). Era 1440
ratchets the lock to the COMPLETE envelope: a 128-byte byte
sequence produced by the JS chunker must parse, reassemble, and
apply identically on the Rust side, and vice versa.

## Objective
1. A `LOCKED_ENVELOPE_BYTES: [u8; 128]` constant in Rust pinning
   a known-good 4-frame envelope.
2. A matching `LOCKED_ENVELOPE_BYTES: Uint8Array` constant in JS.
3. Tests on both substrates that:
   - Parse the bytes into `SporeFrame`s with full CRC validation.
   - Reassemble through the accumulator/reassembler to recover
     the same envelope_hash (`0x9299_32B5`).
   - Apply to an empty sink and verify the resulting anchor.
   - Reject tampered bytes via CRC.
   - Reject truncated streams.
4. JS-side test that re-emits the bytes from a fresh chunker
   call and asserts byte-equality with the locked snapshot.

## Design Notes
- **Why 128 bytes (4 frames)?** Smallest envelope that exercises
  every code path: header chunk + 3 record chunks. Larger
  envelopes would over-stress the locked vector without adding
  coverage; smaller ones would miss the multi-record-chunk
  structure.
- **Why a hardcoded byte vector instead of a generator?** The
  whole point of locked vectors is to detect drift. A generator
  would derive bytes from current code; the test would never
  fail because both sides regenerate from the same drift.
  Hardcoded bytes act as a frozen oracle independent of either
  substrate's current behavior.
- **Why include the JS-emit test (not just JS-parse)?** If only
  Rust tested parse and JS only emitted, a JS regression that
  changed the byte format would silently pass the JS suite (no
  parse test) until the Rust suite caught it via the locked
  snapshot. The mirror "JS emits the locked bytes" test fails
  faster, surfacing the regression on the JS side first.
- **Why the same byte index (40) for the tampering test?** That
  byte sits in the second frame's `proposal_or_target` field —
  changing it definitely breaks CRC. Using the same index across
  substrates locks "tampering at this position breaks parse" as
  a cross-substrate fact, not just a coincidental Rust-side
  invariant.
