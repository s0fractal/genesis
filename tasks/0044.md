Ось систематизований план оптимізації OMEGA-64, базуючись на аналізі вашого коду
(Era 64 / Ontology 42). Розділено за рівнями від критичного до тонкого тюнінгу:

## 1. Критичні: WebGPU Pipeline (CPU↔GPU блокування)

**Проблема:** У `src/lens/phase_compute.ts` метод `readMycelialCentroids()`
створює жорстке блокування через `await stagingBuffer.mapAsync()`:

```typescript
// ЗАРАЗ: Це зупиняє рендер на 1-3мс кожен кадр
await stagingBuffer.mapAsync(GPUMapMode.READ);
```

**Рішення:** Триплексна буферизація (ring buffer) для асинхронного зчитування:

```typescript
// Додати у клас PhaseComputeEngine
private readbackRing: GPUBuffer[] = [];
private ringIndex = 0;

// Ініціалізація 3 буферів
for(let i=0; i<3; i++) {
    this.readbackRing.push(this.device.createBuffer({
        size: 16384,
        usage: GPUBufferUsage.COPY_DST | GPUBufferUsage.MAP_READ
    }));
}

// Використання без await у гарячому циклі
async readMycelialNonBlocking(): Promise<Float32Array | null> {
    const buf = this.readbackRing[this.ringIndex];
    if(buf.mapState === 'unmapped') {
        // Копіюємо, але не чекаємо
        const encoder = this.device.createCommandEncoder();
        encoder.copyBufferToBuffer(this.mycelialBuffer, 0, buf, 0, 16384);
        this.device.queue.submit([encoder.finish()]);
        
        // Переходимо до наступного буфера наступного разу
        this.ringIndex = (this.ringIndex + 1) % 3;
        return null; // Дані ще не готові
    }
    // ... мапінг якщо готовий
}
```

## 2. Високий пріоритет: Compute Shader Memory Barriers

**Проблема:** У `compute_kuramoto.wgsl` ви робите два `compute pass` поспіль з
`clearBuffer` між ними:

```wgsl
// Пас 0: Mycelial Aggregation
pass0.dispatchWorkgroups(...)
// Пас 1: Kuramoto Evolution  
pass1.dispatchWorkgroups(...)
```

Це викликає implicit memory barrier + pipeline flush на GPU.

**Рішення:** Об'єднати в один compute pass з workgroup-level reduction:

```wgsl
// У common.wgsl додати shared memory
var<workgroup> local_bucket_x: array<atomic<i32>, 64>;
var<workgroup> local_bucket_y: array<atomic<i32>, 64>;

@compute @workgroup_size(64)
fn main(@builtin(local_invocation_id) lid: vec3<u32>, ...) {
    // Спочатку агрегація в shared memory
    atomicAdd(&local_bucket_x[lid.x], ...);
    workgroupBarrier(); // Швидше ніж глобальний barrier
    
    // Потім Kuramoto math
    ...
}
```

## 3. Оптимізація Oracle/Senate (LLM шар)

**Проблема:** У `src/ontology/oracle.ts` ви запускаєте 4 паралельні fetch-запити
до LLM без кешування семантичного стану:

```typescript
// ЗАРАЗ: Кожен тик може спамити 4 запити
const maskPromises = MASKS.map(async (mask) => {
    const response = await fetch(OLLAMA_URL, {...}) // Немає кешу!
});
```

**Рішення:** LRU Cache + Semantic Debouncing:

```typescript
// Додати у SovereignOracle
private semanticCache = new Map<string, {result: string, ts: number}>();
private lastSenateHash = 0n;

// Перед викликом LLM перевірити хеш стану системи
const stateHash = this.hashSystemState(entropy, energy, requests);
if(stateHash === this.lastSenateHash && 
   Date.now() - this.lastSenateTime < 5000) {
    return; // Пропускаємо цикл, стан не змінився суттєво
}
```

## 4. WASM Memory Layout (Rust сторона)

**Проблема:** У `granite.rs` структура має padding, але порядок полів не
оптимальний для SIMD:

```rust
// ЗАРАЗ (16 bytes, але з _pad):
pub struct PhaseAgent {
    pub theta: u8,      // +0
    pub energy: u8,     // +1  
    pub omega: i16,     // +2-3
    pub lock: u8,       // +4
    pub entanglement: u8, // +5
    pub _pad: u16,      // +6-7
    pub plasmid: u64,   // +8-15
}
```

**Рішення:** Перегрупувати для 8-byte alignment без explicit padding:

```rust
#[repr(C)]
pub struct PhaseAgent {
    pub plasmid: u64,        // 0-7 (8-byte aligned)
    pub omega: i16,          // 8-9
    pub _pad1: i16,          // 10-11 (для вирівнювання)
    pub theta: u8,           // 12
    pub energy: u8,          // 13
    pub lock: u8,            // 14
    pub entanglement: u8,    // 15
    // Вирівнювання 16 байт досягнуто без зайвих полів
}
```

## 5. TypeScript: Оптимізація Somatic Economy

**Проблема:** У `oracle.ts` метод `tickSomaticEconomy()` перебирає весь
`plasmidRegistry` (Map) кожен кадр:

```typescript
// Це O(n) з великою константою через BigInt
for (const [hash, node] of this.plasmidRegistry.entries()) {
  // ...
}
```

**Рішення:** Spatial Hashing або бакетинг за енергією:

```typescript
// Розділити на "активні" та "сплячі" плазміди
private activePlasmids = new Set<bigint>();
private sleepThreshold = 10;

tickSomaticEconomy() {
    // Оновлювати тільки активні
    for(const hash of this.activePlasmids) {
        const node = this.plasmidRegistry.get(hash);
        if(node.energy < this.sleepThreshold) {
            this.activePlasmids.delete(hash); // Переміщаємо в "сплячі"
        }
    }
}
```

## 6. WGSL: Зменшення Register Pressure

**Проблема:** У `phase_lens.wgsl` ви створюєте багато тимчасових змінних у
vertex shader:

```wgsl
// ЗАРАЗ: Багато проміжних обчислень
let angle = f32(sector) / f32(params.sectors) * 6.2831853;
let radius_t = f32(rho + 1u) / f32(params.radial_bins + 1u);
let major_radius = 2.8 * radius_t;
// ... ще 20 рядків
```

**Рішення:** Precompute в JavaScript та передавати через Storage Buffer:

```typescript
// CPU-side precomputation
const sectorAngles = new Float32Array(SECTORS).map((_, i) =>
  (i / SECTORS) * Math.PI * 2
);
// Передати як окремий буфер замість обчислень у шейдері
```

## 7. Мережевий шар (PhaseNetwork)

**Проблема:** У `phase_network.ts` WebRTC signaling через BroadcastChannel може
створювати "thundering herd" при багатьох табах.

**Рішення:** Exponential backoff + jitter:

```typescript
// Додати до constructor
this.backoffMs = 100 + Math.random() * 200; // Jitter

handleMeshSignal(msg: any) {
    if(msg.type === "HELLO" && this.peers.size > 5) {
        setTimeout(() => this.handleHello(msg), this.backoffMs);
    }
}
```

## 8. Специфічна оптимізація для Chrome/V8

**Проблема:** Часте використання `BigInt` у гарячих шляхах (наприклад
`fnv1a_64`) деградує через heap allocation.

**Рішення:** Для частих хешів використовуйте Number (u53) замість BigInt де
можливо, або кешуйте:

```typescript
// ЗАРАЗ:
const hash = fnv1a_64(intent); // BigInt alloc

// КРАЩЕ (для відомих інтентів):
const INTENT_CACHE = new Map<string, bigint>();
// ...
if (INTENT_CACHE.has(intent)) return INTENT_CACHE.get(intent)!;
```

## Підсумок пріоритетів:

1. **Терміново:** Виправити `readMycelialCentroids` - це ваше головне CPU↔GPU
   bottleneck
2. **Важливо:** Додати кешування до Oracle, щоб не DDoS-ити Ollama
3. **Середнє:** Об'єднати compute passes в WGSL
4. **Файне тюнінг:** Оптимізувати структуру PhaseAgent для кращої кеш-лінійності

Це має підняти FPS з поточних (ймовірно) 30-45 до стабільних 60, особливо на
великих lattice (1400x800).
