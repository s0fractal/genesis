# Task 0144: Era 1580 — Multi-Sink Investigator

## Status: COMPLETED | Priority: HIGH

## Context
Eras 1380-1570 produced the autonomous-investigation loop for
a single sink. Real deployments host several content domains.
Era 1580 generalizes the orchestrator to many sinks with
shared peer-quarantine state.

## Objective
1. `MultiSinkInvestigator` class holding `Map<sink_id,
   AutoInvestigationLoop>`.
2. Per-sink observation routing.
3. `tickAll` and `tickOne`.
4. Global peer exclusion that propagates to existing AND
   future sinks.
5. `sink_id`-tagged emit callback.
6. Aggregated telemetry.

## Design Notes
- **Why per-sink `LoopOptions`?** Different domains have
  different urgency profiles. Financial events may warrant
  short trigger duration + tight cooldown; system alarms may
  tolerate longer dissent windows. Allowing per-sink tuning
  lets operators specialize without forcing a single global
  config.
- **Why is global exclusion shared but per-sink trigger
  cooldowns are NOT?** Cooldowns are about pacing the warrant
  pipeline at the granularity of "one investigation per
  cooldown_ms". A peer who ALSO dissents in another sink
  triggers a SEPARATE investigation in that domain — they're
  semantically independent decisions. Quarantine, in contrast,
  is a peer-level state (the peer is verified bad), which
  applies regardless of domain.
- **Why does the emit callback get `sink_id` metadata?**
  Without it, callers can't know which sink generated a
  proposal — they'd have to maintain external bookkeeping
  matching tick context to emit context. Tagging the proposal
  shifts that responsibility to the multi-sink layer where it
  belongs.
- **Why deterministic sorted-id iteration?** Test
  reproducibility primarily, but also operational sanity:
  operators reading logs see emissions in a stable order
  rather than a hashmap-iteration-dependent jumble.
- **Why are addSink and globalExclude separate operations
  rather than a single `addSink(id, opts, excludedSet)`?**
  The use case is "operator tunes which sinks exist" vs
  "operator quarantines a peer". Conflating them would force
  callers to manage a redundant exclusion list per addSink
  call. Separating gives a cleaner API for each concern.

## Next Era Trigger
**Era 1590: Sink Schema Versioning.** Currently sinks are
identified by free-form `sink_id` strings. Era 1590 will
introduce a `ForensicSinkSchema` (e.g. `"financial-events:v1"`)
that:
- Marks each sink's content domain explicitly.
- Refuses cross-sink delta merges where schemas mismatch.
- Tracks per-schema convergence telemetry separately so
  operators can spot domain-specific lag.
- Enables versioned schema migrations (sink "financial-events:v1"
  → "financial-events:v2") with explicit migration paths.
