# Task 0135: Era 1490 — ConvergenceDriver Auto-Pipeline

## Status: COMPLETED | Priority: HIGH

## Context
Era 1480 had all the primitives wired but a caller still had to
drive the state machine manually. Era 1490 wraps that into a
single `step()` call so a spore's main loop becomes two function
calls (runner.step + pipeline.step) for full convergence behavior.

## Objective
1. `AutoPipeline<const M>` wrapping `ConvergenceDriver<M>` with
   pending-request state.
2. Three-phase tick:
   - Phase 1: drain completed peer hash list, compute diff, ship.
   - Phase 2: time out stale pending request.
   - Phase 3: idle → pick next target + issue HASH_REQUEST.
3. Deterministic `generate_request_id` via FNV-1a.
4. Tests covering happy path, timeout, idle behavior.

### 2. Phase Behavior ✅
- [x] Phase 1: matches `take_peer_hashes` request_id with our

- [x] Phase 3: only fires when no request pending; calls
  `select_targets`; if a target found, issues HASH_REQUEST +

## Design Notes
- **Why `pending_request_id == 0` as the idle sentinel?**
  `generate_request_id` ensures the output is never 0, so we can
  use 0 unambiguously to mean "no in-flight request". Avoids a
  separate Boolean.
- **Why does `complete_request` not update peer's `last_seen_anchor`?**
  Two reasons. First, after a diff ship, B may still have stuff
  A doesn't (asymmetric divergence) — A doesn't know B's new
  anchor without another HASH_LIST. Second, the peer will
  broadcast its updated anchor in a periodic HASH_LIST anyway;
  recording it on completion would be redundant and risk drift.
- **Why FNV for request_id instead of a counter?** A counter
  would collide across reboots without persistence. Hashing
  `(self_relay_id, now_ms)` gives uniqueness without state.
- **Why only one in-flight request per pipeline?** Multiple
  concurrent requests would require parallel reassemblers
  (n×HashListAccumulator). On a tiny spore that's wasteful;
  serial requests through one accumulator capacity work fine
  for the typical fanout (8-16 peers, ~10s latency per
  exchange).
- **Why `record_sync_attempt` on Phase 3 issue but `record_sync_success`
  on Phase 1 completion?** Symmetric with the manual-driver
  pattern from Era 1460: attempt is "we asked", success/failure
  is "outcome known". A timeout in between is the failure path.
