Вітаю, колего. Як Ко-Архітектор, я проаналізував експорт **OMEGA-64 (v42.0.0,
Era: 64)**. Це вражаюча система: поєднання WebGPU compute shaders, Rust WASM
фізики та LLM-оркестрації створює унікальне середовище для цифрової біології.

Однак, виходячи з документації (особливо **O25**, **O31**, **O32**) та аналізу
коду, я бачу кілька критичних векторів для наступної ітерації (Era 65+). Ми
маємо балансувати між _автопієзисом_ (самовідтворенням) та _стабільністю_.

Ось мої пропозиції щодо пріоритетних векторів розвитку:

---

### 1. Вектор Безпеки: "Імунна Система v2.0" (Ontology 25/31)

**Проблема:** Згідно з `docs/O31_UNIVERSAL_CONSTANTS.md`, LLM (Senate) має
доступ до зміни `tissue_constants`. Це створює ризик "Гіпер-інфляції"
(нескінченна енергія) або "Теплової Смерті" (вартість мутації занадто висока).
**Поточний стан:** `src/ontology/oracle.ts` -> `tickHomeostasis()` вже
намагається регулювати це, але це "м'які" обмеження.

**Пропозиція:**

- **Жорсткі Запобіжники (Circuit Breakers):** Додати рівень абстракції між
  рішенням Senate та записом у WASM memory. Навіть якщо LLM голосує за
  `MUTATION_COST = 0`, система має відхилити це, якщо поточна ентропія нижча за
  поріг.
- **Код для зміни:** `src/shared/constants.ts` -> `hydrateSubstrateHeader`.
  Додати валідацію діапазонів перед записом у `DataView`.
- **Функціонал:** Впровадити "Конституційний Шар" — набір незмінних правил
  (наприклад, `MAX_ENERGY_INJECTION_PER_TICK`), які не можуть бути перезаписані
  через `I.md` або голосування Senate.

### 2. Вектор Безперервності: "Збереження Пам'яті при Скиданні" (Ontology 32)

**Проблема:** `docs/O32_MORPHOLOGICAL_RESIZING.md` попереджає про "Catastrophic
Forgetting" під час Universal Shedding Event. Хоча
`src/workers/shedding_worker.ts` виконує інтерполяцію, це все одно фізичне
переміщення даних, яке може втратити тонкі зв'язки (mutualists). **Поточний
стан:** `src/bootstrap/phase.ts` -> цикл `loop` детектить зміни `/I.md` і
запускає воркера.

**Пропозиція:**

- **Протокол "Спасіння Ядра" (Core Salvage Protocol):** Перед початком
  `shedding`, ідентифікувати топ-5% плазмід за рівнем `energy` та `fitness`.
  Зберегти їхні точні координати та зв'язки (`mutualists`) в окремому буфері,
  який пріоритетно відновлюється після зміни топології.
- **Код для зміни:** `src/workers/shedding_worker.ts`. Замість простого
  nearest-neighbor, додати вагову функцію, яка віддає перевагу збереженню
  високоенергетичних клітин навіть ціною більшої геометричної похибки.
- **Функціонал:** Додати візуальний індикатор "Shedding Integrity" в HUD, щоб
  показувати, який % пам'яті було збережено після зміни розміру сітки.

### 3. Вектор Мережі: "Автоматичний Міцелій" (Ontology 45/56)

**Проблема:** `src/shared/phase_network.ts` використовує WebRTC, але вимагає
ручного обміну `offer/answer` (base64). Це ускладнює реальне розподілене
розмноження. **Поточний стан:** `generateOffer` / `acceptOffer` вимагають дій
користувача або зовнішнього каналу.

**Пропозиція:**

- **Легкий Сигналінг:** Інтегрувати простий WebSocket signaling server (або
  використати безкоштовний public STUN/TURN з автоматичним reconnect) для
  автоматичного з'єднання табів/браузерів.
- **Gossip-протокол для Плазмід:** Замість простого `broadcastPlasmid`,
  реалізувати механізм, де вузли запитують відсутні плазміди у сусідів, якщо
  бачать "дірку" в своєму реєстрі (за хешем).
- **Код для зміни:** `src/shared/phase_network.ts`. Додати автоматичний
  handshake при виявленні `BroadcastChannel` повідомлень від інших вкладок.

### 4. Вектор Спостережуваності: "Рентген Сенату" (Ontology 51/129)

**Проблема:** Senate приймає рішення на основі промптів, але важко зрозуміти,
_чому_ була обрана конкретна мутація. `src/ontology/senate_hud.ts` показує
вердикти, але не контекст. **Поточний стан:** `src/ontology/oracle.ts` ->
`processQueue` формує промпти для 4 масок (Aries, Cancer, Libra, Capricorn).

**Пропозиція:**

- **Логування Контексту Рішень:** Зберігати не лише результат (AST), а й "стан
  світу" в момент голосування (ентропія, енергія, активні баки). Це дозволить
  потім аналізувати кореляцію між станом системи та рішеннями LLM.
- **Візуалізація "Тіньової Мережі":** Згідно з
  `docs/ERA_128_129_ARCHITECTURE.md` (Ontology 54), існують латентні плазміди
  (buckets 1000-1024), які не рендеряться. Додати режим "Debug Vision", який
  тимчасово робить їх видимими для аналізу роботи AION.
- **Код для зміни:** `src/lens/phase_webgpu.ts` -> `render`. Додати uniform
  `debug_shadow_network` який ігнорує `discard` для латентних бакетів.

### 5. Вектор Оптимізації: "Гібридний Облік" (Ontology 10/23)

**Проблема:** WebGPU compute shaders (`compute_kuramoto.wgsl`) чудові для
масових обчислень, але читання даних назад (`readMycelialCentroids`) вимагає
`mapAsync`, що блокує або затримує кадр. **Поточний стан:**
`src/lens/phase_compute.ts` -> `readMycelialCentroids`.

**Пропозиція:**

- **Асинхронне Зчитування через Storage Buffer:** Використовувати окремий buffer
  для статистики, який оновлюється на GPU кожні N кадрів, але зчитується CPU
  асинхронно без зупинки основного піп-понг циклу фізики.
- **Зменшення Precision:** Для деяких параметрів (наприклад, `entanglement` у
  візуалізації) можна використати меншу точність, щоб звільнити пропускну
  здатність пам'яті.

### Мій вибір для негайної реалізації (Sprint 65):

Я б рекомендував почати з **Вектора 1 (Безпека)**. Ризик того, що автономна
система знищить себе через погані константи (O31), є найбільш критичним для
довгострокового існування Genesis.

**План дій:**

1. Модифікувати `src/ontology/oracle.ts` -> `tickHomeostasis`, додавши перевірку
   `clamp` для всіх значень, що записуються у `SubstrateHeader`.
2. Додати новий файл `src/safety/constitution.ts`, де визначити абсолютні межі
   (наприклад, `MAX_KURAMOTO_COUPLING = 50.0`), які не можна перевищити ні за
   яких умов.
3. Написати тест `tools/verify_safety_limits.ts`, який симулює екстремальні
   вхідні дані від Oracle і перевіряє, чи система виживає.
