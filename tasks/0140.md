# Task 0140: Era 1540 — Auto-Warrant Issuance from Quorum Trigger

## Status: COMPLETED | Priority: HIGH

## Context
Era 1530 produces `fire_now` peer_ids ready for forensic
investigation. Era 1540 converts each into a `WARRANT_PROPOSAL`
payload compatible with Era 1090's existing oracle warrant gate.

## Objective
1. `QuorumWarrantBridge` class consuming `TriggerOutcome` and
   producing `WarrantProposalPayload[]`.
2. Deterministic warrant descriptions of the form
   `INV peer=0x{peer:08x} consensus=0x{anchor:08x}`.
3. `senateHash` byte-identical to `WebRTCV2Mesh.senateHash`.
4. Per-peer dedup window for defense-in-depth.

## Design Notes
- **Why a separate `senateHash` instead of importing
  `WebRTCV2Mesh.senateHash`?** Avoids a dependency cycle —
  `WebRTCV2Mesh` imports many forensic-stack modules; pulling
  it into the warrant bridge would create import bookkeeping
  pain. The cross-module integration test asserts the two
  copies stay byte-equal. If they ever drift, both suites
  break simultaneously.
- **Why deterministic description format?** Two operators with
  identical observations produce identical proposalHash values,
  so the senate ledger dedupes naturally across the mesh. A
  free-form description would create one warrant per operator,
  drowning the oracle gate in duplicates.
- **Why dedup IN ADDITION TO Era 1530's cooldown?** Era 1530's
  cooldown is about pacing trigger evaluations. Era 1540's
  dedup is about pacing warrant emissions. They're at different
  layers — the cooldown might not fire if the caller lost a
  `markTriggered` call (race condition); the bridge's dedup
  catches that case before the oracle pipeline gets flooded.
- **Why include `consensus_anchor` in the description?** Two
  legitimate scenarios produce different warrants for the
  same peer:
  1. Peer dissents on consensus A → warrant_A.
  2. Mesh moves to consensus B; peer still dissents → warrant_B.
  Including the anchor in the description gives each scenario
  a distinct proposalHash so they don't dedupe against each
  other in the senate ledger.
- **Why is `WarrantProposalPayload` a subset of `PlasmidPayload`,
  not the full type?** Plasmids carry many transport-level
  fields (attractorAddress, matrix, recursionDepth) that the
  bridge can't sensibly fill. Caller merges the warrant
  payload into a plasmid template before enqueuing. Keeps the
  bridge simple and doesn't tie it to plasmid layout
  evolution.
