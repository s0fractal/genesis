# Task 0145: Era 1590 — Forensic Sink Schema Versioning

## Status: COMPLETED | Priority: HIGH

## Context
Era 1580 routes sinks by opaque string id. Real deployments
need explicit content-domain identification so cross-sink
operations can be validated against compatible-schema rules.

## Objective
1. `ForensicSinkSchema` `{name, major, minor}` shape.
2. `parseSinkSchema(string)` / `formatSinkSchema(schema)` /
   `isValidSinkSchemaString(string)`.
3. `compatibleSchemas` predicate (same name + same major).
4. `SinkSchemaRegistry` with register/get/sinksByName/
   compatibleSinks/summary/size.

## Acceptance Criteria

### 1. Format ✅
- [x] Pattern: `name:vMAJOR.MINOR` where name ∈
  `[a-zA-Z0-9_-]{1..32}` and versions are non-negative ints.
- [x] Roundtrip: `formatSinkSchema(parseSinkSchema(s)) === s`.

### 2. Parsing ✅
- [x] Valid strings parsed correctly.
- [x] Malformed inputs return `null` (no throw):
  - empty string
  - missing version
  - missing 'v' prefix
  - non-numeric components
  - whitespace
  - invalid chars in name
  - name longer than 32 chars
  - non-string input (null/undefined/number)
- [x] Max-length name (32 chars) accepted.

### 3. Compatibility ✅
- [x] Same name + same major → true (minor permissive).
- [x] Same name + different major → false.
- [x] Different name → false.
- [x] `compatibleSchemaStrings` convenience returns false on
  malformed input.
- [x] `sameSinkSchema` for full equality (incl. minor).

### 4. Registry ✅
- [x] `register(sink_id, schema_string)` parses + stores;
  throws on malformed schema; throws on duplicate sink_id.
- [x] `unregister`, `get`, `size`.
- [x] `sinksByName(name)` returns sorted list of ids.
- [x] `compatibleSinks(schema)` returns sorted list of ids
  matching name + major.
- [x] `summary()` returns sorted list of
  `{schema, sink_count}` aggregations.

### 5. Tests ✅
- [x] 22 Deno tests covering: parse valid + many malformed
  cases (empty/missing-version/missing-v/non-numeric/whitespace/
  bad-char/too-long/non-string), max-length name, format
  roundtrip, isValid predicate, compatibility (same-major-true/
  different-major-false/different-name-false), convenience
  string overload + invalid-input rejection, sameSinkSchema,
  registry register/get/throws on malformed/throws on duplicate/

## Design Notes
- **Why permissive minor + strict major?** Convention: minor
  bumps are additive (new optional fields, telemetry tweaks);
  major bumps are breaking (record layout changes, semantic
  shifts). A v1.0 sink applying a v1.5 record should succeed
  unchanged because the v1.0 fields are still all there. A
  v1.0 sink applying a v2.0 record would silently misinterpret
  bytes — refuse it.
- **Why a regex-based parser instead of a richer grammar?**
  The format is simple and predictable. A regex with a single
  capture pattern is faster, smaller, and easier to verify
  visually than a hand-rolled state machine. The cost is the
  inability to extend (e.g. add tags after the version), but
  YAGNI — if a future Era needs richer schemas, the parser can
  be replaced wholesale.
- **Why throw on duplicate registration instead of overwriting?**
  Programmer error. Two sinks with the same id is never what
  the operator wants — it's a config bug or a copy-paste
  mistake. Failing loudly catches it at startup; silent
  overwrite would create a debugging nightmare months later.
- **Why a separate registry class instead of attaching schema
  to MultiSinkInvestigator?** Decoupling. The schema layer is
  a *property* of sinks; the multi-sink layer is *orchestration*
  over loops. Letting them combine (or not) at the integration
  level keeps each module focused.
- **Why does `compatibleSinks` use a parsed `ForensicSinkSchema`
  parameter while `register` takes a string?** Common usage
  patterns: register-time inputs come from config files (string
  data), but compatibility queries inside hot paths usually
  already have a parsed schema in hand. Mixing both shapes lets
  callers avoid redundant parses.
