# Task 0136: Era 1500 — WebRTC Event Bridge

## Status: COMPLETED | Priority: HIGH

## Context
Eras 1380-1490 produced the forensic-event convergence stack
running on JS (in-process) and Cortex-M4F (UART/SPI/BLE). Era
1500 connects browser peers to the same protocol over WebRTC
DataChannels via a transport-agnostic bridge.

## Objective
1. `WebRTCEventBridge` class wrapping Era 1380's
   `ForensicEventSink` + Era 1390's pure sync functions.
2. `BridgeTransport` interface so the bridge can be tested
   without instantiating real RTCPeerConnections.
3. Three-message protocol: `PEER_HELLO`, `HASH_LIST`, `DELTA`.
4. Automatic DELTA-back on HASH_LIST receipt.
5. Telemetry counters for HUD wiring.

## Design Notes
- **Why not extend `WebRTCV2Mesh` directly?** Two reasons.
  First, the existing mesh handles plasmid routing with
  hop-count + hyperbolic distance — semantics that don't
  apply to bridge messages (peer-to-peer, not multi-hop).
  Second, a transport-agnostic bridge can be reused for
  non-WebRTC backends (SSE, WebSocket, in-process tests)
  without dragging mesh assumptions along. Era 1510 will
  adapt the bridge into the mesh as a separate plasmid type.
- **Why peer-known gating instead of fire-and-forget?**
  WebRTC raises errors when sending on unconnected channels;
  silently dropping at the bridge layer is better than
  surfacing transport exceptions. The handshake (HELLO or
  first HASH_LIST) primes the gate.
- **Why JSON-encoded discriminated union instead of binary?**
  WebRTC DataChannels work natively with strings or
  ArrayBuffers; JSON keeps the wire format human-debuggable
  and trivially serializable. Binary encoding (e.g. CBOR)
  would shave bytes but complicates wireshark-style debugging.
  At convergence-rate cadences (Hz, not kHz), JSON is fine.
- **Why does HELLO send-on-receive update the known set?**
  HELLO is a courtesy; HASH_LIST and DELTA implicitly
  identify the sender via `from`. Treating any incoming
  message as proof-of-handshake makes the bridge resilient
  to lost HELLOs (DataChannels can drop messages during
  setup).
- **Why is `sendDelta` exposed as a public method?** Higher
  layers (e.g. Era 1340 coordinator running in browser) may
  want to ship specific entries to a peer based on their
  own logic, bypassing the auto-response path. Exposing it
  lets the bridge serve both reactive and explicit use cases.
