# Task 0129: Era 1430 — Spore Event Sync Loop

## Status: COMPLETED | Priority: HIGH

## Context
Era 1420 added Cortex-M4F encode primitives. Era 1430 ports the
decode/apply/schedule path. With this Era, two spores connected
by UART loopback have all the code they need to converge their
event sets without any JS relay in between.

## Objective
1. `EventDeltaAccumulator<const C>` — `no_std` reassembler with
   out-of-order, dedup, corruption-detect, cross-envelope-filter
   semantics matching JS `reassembleEventDelta`.
2. `apply_event_delta` — two-phase merger (collision check first,
   then mutate) preserving local sink integrity on failure.
3. `PeerSyncSlot` + scheduler ops — Era 1330 ported onto fixed
   table.
4. End-to-end smoke test: two sinks, build → accumulate → apply
   on each side, anchors match.

## Design Notes
- **Why two-phase apply (collision check before mutation)?** The
  JS implementation also splits these phases. Mutating then
  rolling back would require the sink to be transactional, which
  is heavy for a no_std structure. Walking entries twice is O(N²)
  in the worst case but `N` is bounded by accumulator capacity
  (typically <32) so the cost is trivial in practice.
- **Why does `take_delta` reset the accumulator on success?** A
  spore's RAM is precious. Holding a completed envelope occupies
  capacity that could be reassembling the next one. Forcing the
  caller to consume + apply before requesting another envelope
  is also a clear protocol contract.
- **Why does `take_delta` return `None` on envelope_hash drift
  instead of a typed error?** The accumulator's signals are
  already encoded in `AccumulateOutcome`. Drift detection at
  `take_delta` time covers a different case (consistent frames
  with valid CRCs that nonetheless don't reconstruct to the
  claimed envelope_hash) and is rare enough that "no delta"
  is a clean answer for the caller — it should reset and retry.
- **Why are scheduler operations bare functions instead of
  methods?** `no_std` ergonomics. `PeerSyncSlot` is just data;
  the operations on it don't need ownership. Bare functions
  match the existing pattern from `forensic_event_sink.rs` and
  let the caller manage the table layout however suits their
  stack budget.
- **Why `[PeerSyncSlot; N]` instead of a Map-like structure?**
  No allocator. A spore that tracks 8-16 peers fits the table
  trivially in SRAM. Linear-scan lookup by peer_id is fast
  enough at that scale. If a future Era needs hundreds of peers,
  a sorted-slice search can be added without changing the
  PeerSyncSlot contract.
