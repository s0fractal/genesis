## 1. Executive Diagnosis

OMEGA-64 зараз переходить із "внутрішньої лабораторії" у форму, яку можна
показувати назовні. Kimi правильно вибрала Living Museum як перший публічний
вектор: він мінімізує trust surface, обходить незавершений production ZK,
не потребує live mesh, але демонструє головну силу системи — детерміністичне
живе поле, яке можна перевіряти.

| Вісь | Оцінка | Коментар |
|------|--------|----------|

борги.

## 2. Вектор A — Determinism & Cross-Substrate Physics

### Стан

Це центральний актив OMEGA-64. Після виправлення read-after-write у Rust
`tick_physics()` старий chunk-buffer більше не викривляє сусідські reads на
межах chunk-ів. `tick_snapshot_ptr` робить snapshot source явним для тестів і
runtime. `compute_toroidal.wgsl` тепер відповідає Rust не тільки за Kuramoto
coupling і metabolic burn, а й за attractor drift.

### Чому це важливо

Без exact parity Golden Trace перестає бути консенсусним фактом. Drift у shader
не завжди видно в UI, але він руйнує replay, forensic audit і ZK claims. Новий
WGSL harness переводить цей ризик із "ручного відчуття" в executable guard.

### Ризики

| Ризик | Ступінь | Коментар |
|-------|---------|----------|
| Static global leakage у Rust tests/runtime | Високий | `ATTRACTOR_ARRAY`, `PHI_MESSAGE_BUFFER`, snapshots потребують явних reset boundaries. |
| Q-phase mismatch | Середній | LUT Q10 256 entries працює для parity, але topology q_phase може бути <8. |
| Attractor semantics drift | Середній | Rust і WGSL тепер узгоджені, але `compute_v2.wgsl` може мати іншу семантику. |
| Golden trace partial sampling | Середній | 32 samples швидко, але не доводить повну state equality. |

### Рекомендації

1. Додати multi-tick WGSL harness: 1, 2, 8, 64 ticks.
2. Додати кілька topology cases: q_phase 2, 5, 7, 8.
3. Додати parity mode з 0, 1 і 4 attractors.
4. Розділити `LAST_SNAPSHOT_MEMORY` для delta snapshots і tick snapshots у runtime naming, щоб уникати semantic overload.
5. Ввести `v2_reset_runtime_state()` для тестів, demo boot і майбутніх deterministic scenarios.

## 3. Вектор B — Living Museum

### Стан

без mesh, oracle worker, ATP bridge і live Senate side effects. Це хороша

### Найсильніше рішення

Museum використовує production renderer і production WASM bridge, але запускає
їх у зменшеному trust/performance profile. Це добре: demo не стає окремою
іграшкою, а тестує реальний core.

### Поточні слабкі місця

| Проблема | Наслідок |

| No browser visual regression | Build зелений, але canvas framing не перевірений screenshot-ами. |
| Export witness не містить enough reproducibility inputs | Є trace/tick/genesis, але немає seed, attractor array, q topology. |

### Що варто доробити

1. Witness v2:
   - `seed`
   - `q_phase/q_sectors/q_radial`
   - `attractors`
   - `agent_count`
   - `compute_mode`
   - `wasm_size` або `wasm_hash`
2. HUD should expose:
   - FPS
   - WebGPU adapter label якщо доступний
   - parity mode: `TOROIDAL/RUST-LOCKED`
3. Add visual state:
   - attractor count and last preset
   - paused overlay
   - WebGPU unavailable full-page fallback, not `alert()`
4. Додати Playwright/browser-use smoke:
   - `dist/museum.html` loads
   - canvas nonblank
   - click changes Golden Trace within N frames
   - export witness has valid schema

## 4. Вектор C — Renderer & GPU Runtime

### Стан

Kimi правильно прибрала дві performance-пастки:

- per-frame bind group allocation
- unthrottled GPU readback

Також daemon intent clear переведено з `setTimeout` у frame-synchronized
deadline. Це краще для deterministic feel і runtime predictability.

### Архітектурне зауваження

`v2_renderer.ts` стає central orchestration god-object: compute mode, render
pass, daemon, readback, Golden Trace, memory guard, attractors. Це допустимо
для швидкого Museum, але небезпечно для довгої підтримки.

### Рекомендований split

| Module | Відповідальність |
|--------|------------------|
| `renderer_buffers.ts` | GPUBuffer creation, ping-pong state, bind groups. |
| `renderer_readback.ts` | snapshot throttle, staging buffer, Golden Trace sync. |
| `renderer_daemon.ts` | autonomous intent rules. |
| `renderer_modes.ts` | V2 vs toroidal compute switching. |
| `v2_renderer.ts` | thin coordinator. |

Не робити це зараз, якщо ціль — швидкий public Museum. Але зафіксувати як
Era 0204/0205, інакше наступні GPU features будуть додаватися у вже великий
клас.

## 5. Вектор D — WebRTC Mesh & Security Boundary

### Стан

Async burn queue зменшує head-of-line blocking. Default `MockATPBridge` робить
локальний/dev runtime менш крихким. Deterministic handshake proof stub краще за
literal mock string, бо він peer-specific і genesis-bound.

Але важливо: **це не security proof**.

### Trust boundary reality

| Компонент | Поточний рівень |
|-----------|-----------------|
| Handshake ZK | Stub, not trustable |
| ATP burn verification | Mock by default |
| SP1 integration | Not end-to-end in live mesh |
| Peer admission | Weak |
| Message validation | Partial |

### Практичний висновок

Public Museum можна запускати. Public permissionless mesh — ні. Mesh має бути
або disabled, або private allowlisted, доки handshake не стане реальним.

### Мінімальний production gate

1. Replace deterministic stub with real verifier or signed admission token.
2. Make `MockATPBridge` explicit dev-only:
   - e.g. constructor requires `{ mode: "dev" }`
   - production default must fail closed
3. Rate-limit inbound plasmids per channel.
4. Add replay protection for `burn_tx_hash`.
5. Add tests for:
   - concurrent identical burn hash dedup
   - invalid proof rejection
   - delayed burn verification does not block `IMPACT_EVENT`

## 6. Вектор E — ZK / SP1 / Proof Economy

### Стан

ZK story conceptually strong, implementation uneven. `mitosis_proof.rs` and
receipt hashing are valuable because they isolate pure derivation. Але live
mesh still does not enforce real SP1 proof admission.

### Найкращий next step

Не будувати "повну ZK economy" одразу. Спочатку зробити один narrow vertical:

```text
parent + attractor_array + q_phase
        ↓
derive_mitosis_child()
        ↓
SP1 guest proof
        ↓
host verifies receipt
        ↓
WebRTC plasmid accepted
```

### Чому narrow vertical

Бо OMEGA має багато протоколів, і broad ZK integration швидко стане
інтеграційною трясовиною. Один доведений mitosis path створить реальний trust
anchor, який можна розширювати.

### Definition of Done для ZK slice

- guest test exists
- host verifies proof in CI or marked expensive/manual
- TS verifier rejects malformed proof bytes
- mesh path has no "accept if string length > N" behavior
- receipt hash anchored in forensic sink

## 8. Вектор G — Release Engineering & Artifact Lifecycle

### Стан

До виправлення `emptyOutDir: false` build pipeline мав прихований дефект:
`build:wasm` писав `dist/v2/omega_v2_core.wasm`, а `vite build` міг стерти
`dist/`. Це саме той клас багів, який не видно в TypeScript/Rust tests, але
ламає deployed demo.

### Рекомендована build policy

1. `deno task build:wasm` writes to stable `dist/v2`.
2. Vite не чистить `dist/v2`.
3. Post-build check:

```bash
test -f dist/v2/omega_v2_core.wasm
test -f dist/museum.html
```

4. Add `deno task verify:dist`.
5. Add `wasm_hash` file:

```text
dist/v2/omega_v2_core.wasm.sha256
```

Це дасть Museum witness можливість посилатися на конкретний WASM artifact.

## 16. Final Position

OMEGA-64 не треба поспішати ставати "production decentralized life network".
Його сильніший immediate move — стати **publicly inspectable deterministic
life instrument**. Living Museum робить саме це.

Правильна стратегія:

1. Публічно показати те, що вже реально сильне: deterministic lattice,
   Golden Trace, attractor perturbation, witness export.
2. Чітко маркувати те, що ще roadmap: real ZK mesh admission, ATP economy,
   live oracle governance.
3. Методично перетворити найслабші narrative claims у executable guarantees.

Якщо тримати цей порядок, OMEGA-64 не розмиє себе broad обіцянками і зможе
зберегти головну перевагу: рідкісне поєднання математичного детермінізму,
філософської сили і реального cross-substrate engineering.
